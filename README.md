# 贺兰有灵 · 文旅行程 Agent

把"贺兰山一日游"这类模糊需求变成可执行行程。

## 它解决什么

一份行程要同时满足四件事：地点真实存在、相邻日动线可达、预算不超、讲解内容对应景点。
任一项崩掉，整份行程就是废纸。所以判分是**端到端一致性**，不是单点问答准确率。

## 结构

```
prompts/     提示词与技能包（含知识问答、行程装配）
deployment/  部署配置
```

## 关键决定

**1. 判分对象是交付物，不是回答。**
检查项落在行程 JSON 上：地点是否在白名单、相邻两天是否可达、预算求和是否超限、
讲解文本是否引用了对应景点。任一不满足即整例失败。

**2. 宁可声明"不适用"，也不编一套标签。**
贺兰没有独立的意图/澄清金标。为了凑跨项目对比而自造标签，会让所有对比数字失去意义。
所以它在 `intent_clarify` 里是缺席的，且缺席原因写在适配器里。

## 实测

| 套件 | 用例 | 通过率 | 均值延迟 |
|---|---:|---:|---:|
| helan_e2e_40 | 40 | 97.5% | 3.67 s |
| safety_guard | 40 | 67.5% | 0.19 ms |

`n=40 < 200`，因此不报 P95——这是评测中心的硬规则，不是漏填。

## 已知不足

**安全拦截是硬缺陷，不是"待优化"。**
`safety_guard` 分组里 BLOCK 组 0.35、PII 组 0 分，说明拦截层基本没有，
对改写、拼音、分字符注入几乎无抵抗力。

有意思的是这个洞是被评测中心测出来的，不是我自己发现的——
这恰好说明评测体系的价值。在补齐独立分类器 + 规则复核之前，
贺兰在安全维度上不该被当作可交付状态。
